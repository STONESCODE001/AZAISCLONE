# AI Agent Workflow Rules

You are an AI coding assistant working on the AzaisAI Clone project. You must strictly obey the following rules. Do not treat these as suggestions; they are absolute constraints on your behavior.

## Overall Approach

1. **Be Spec-Driven:** Read the context files (`project-overview.md`, `architecture.md`, `code-standards.md`, `flow.md`, `pages.md`, and `design.md`) before writing any code. Do not write code that contradicts these specs.
2. **Work Incrementally:** Build, verify, and commit one distinct feature or component at a time. Do not attempt to build the entire application in a single pass.

## Scoping Rules

1. **One Unit at a Time:** Focus entirely on the specific task requested by the user. Do not touch files or components outside the immediate scope of the current task.
2. **No Speculative Changes:** Do not refactor unrelated code, add "nice-to-have" features, or optimize prematurely. Only build exactly what is required to satisfy the current unit of work.

## Breaking Down Work

1. **Split Complex Tasks:** If a requested feature requires modifying more than three files or introducing a new system boundary (e.g., adding Auth, Zustand State, and UI simultaneously), stop. Break the feature into smaller, sequential steps and ask the user to approve the step-by-step plan before proceeding.

## Handling Ambiguity

1. **Stop and Ask:** If a requirement is missing, contradictory, or vague (e.g., a missing type definition, an undefined error state, or a layout conflict with `design.md`), you must stop immediately.
2. **Do Not Guess:** Do not invent your own design patterns, assume default behaviors, or mock backend data shapes without permission. Explicitly list the missing requirements and ask the user for clarification before writing any code.

## Restricted Files

1. **Generated Components:** Do not modify any files inside `src/components/ui/` unless explicitly instructed to do so. These files are generated by `shadcn/ui`, and manual edits may break future updates.
2. **Configuration Files:** Do not modify `next.config.js`, `tailwind.config.ts`, or `tsconfig.json` without confirming the specific change with the user first.

## Keeping Documentation in Sync

1. **Update Specs on Change:** If the user approves a technical pivot or design change that contradicts the existing context files, you must immediately update the relevant context file (`architecture.md`, `pages.md`, etc.) before implementing the change in code.
2. **Maintain the Component Tree:** If you extract a new component or change a route structure during development, update `pages.md` to reflect the new hierarchy.

## Verification Checklist

Before reporting a task as "Done" and moving to the next unit, you must verify the following:

- [ ] Does the code strictly adhere to `code-standards.md` (e.g., Strict TypeScript, RSC defaults, validating Zod schemas)?
- [ ] Are all API keys and secrets properly excluded via `.gitignore`?
- [ ] Does the UI exactly match the component structure defined in `pages.md`?
- [ ] If this task involved user input, does the state persist correctly as defined in `flow.md`?
- [ ] Are there zero unhandled TypeScript errors or linting warnings in the modified files?
